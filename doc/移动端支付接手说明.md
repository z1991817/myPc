# 移动端支付接手说明

> 适用版本：v0.0.1  
> 前端页面：`pages/checkout/index.tsx`  
> 接口文件：`api/recharge.ts`  
> 支付接口：`POST /app/recharge/orders`

---

## 1. 这份文档解决什么问题

这份文档只说明当前前端在移动端环境下是怎么发起支付、怎么回跳恢复、怎么轮询订单状态的，方便后续接手的人快速定位和修改。

如果要看接口字段定义，可以继续看：

- `doc/支付前端接口调用文档.md`
- `doc/项目接口调用清单-按页面.md`

## 2. 当前代码入口

| 功能 | 文件 | 关键点 |
|---|---|---|
| 支付页 UI、支付环境判断、跳转、轮询 | `pages/checkout/index.tsx` | 核心逻辑都在这里 |
| 创建订单、查订单详情 | `api/recharge.ts` | `createRechargeOrder`、`getRechargeOrderDetail` |
| 支付回跳后的订单页登录恢复提示 | `pages/my-orders/index.tsx` | 读取 `checkout-payment-return` |

最重要的函数：

| 函数/常量 | 作用 |
|---|---|
| `resolvePayType()` | 根据浏览器 UA 判断支付类型 |
| `handlePurchase(planId)` | 点击购买后的完整支付发起流程 |
| `pollOrderStatus(orderId)` | 轮询订单状态 |
| `PENDING_PAYMENT_STORAGE_KEY` | 保存未完成支付订单 |
| `PAYMENT_RETURN_MARKER_KEY` | 标记用户从支付页跳出去，后续需要恢复订单状态 |

## 3. payType 判断规则

移动端当前涉及 2 种 `payType`：

| 环境 | 判断方式 | payType | 当前前端行为 |
|---|---|---:|---|
| 微信内置浏览器 | UA 包含 `MicroMessenger` | 1 | 当前页面跳转到后端返回的 `payUrl` |
| 普通移动端浏览器 | UA 匹配 `Android/iPhone/iPad/iPod/Mobile/Windows Phone` | 3 | 优先新窗口打开 `payUrl`，失败后当前页面跳转 |

对应代码。下面只保留移动端相关判断，源码里还有非移动端兜底：

```ts
const isWechatBrowser = (userAgent: string) =>
  /MicroMessenger/i.test(userAgent);

const isMobileBrowser = (userAgent: string) =>
  /Android|iPhone|iPad|iPod|Mobile|Windows Phone/i.test(userAgent);

const resolvePayType = (): PayType => {
  const userAgent = window.navigator.userAgent;

  if (isWechatBrowser(userAgent)) {
    return 1;
  }

  if (isMobileBrowser(userAgent)) {
    return 3;
  }
};
```

注意：`doc/支付前端接口调用文档.md` 里提到了 `payType = 11` 支付宝 H5，但当前移动端代码还没有支付宝 H5 分支。

## 4. 移动端支付主流程

用户在 `/checkout` 点击套餐的“立即购买”后，流程如下：

```text
点击购买
  ↓
检查是否已登录
  ↓
resolvePayType() 判断当前环境
  ↓
POST /app/recharge/orders
请求体：{ packageId, payType }
  ↓
后端返回 orderId + payUrl
  ↓
写入 sessionStorage：
  - checkout-pending-payment
  - checkout-payment-return
  ↓
根据 payType 处理：
  - payType = 1：当前页面跳转 payUrl
  - payType = 3：优先新窗口打开 payUrl，失败后当前页面跳转 payUrl
```

移动端相关代码在 `handlePurchase` 中。理解时可以按下面这个等价逻辑看：

```ts
if (payType === 3) {
  markPaymentReturn();
  const paymentWindow = window.open(
    payUrl,
    "_blank",
    "noopener,noreferrer",
  );

  if (paymentWindow) {
    paymentWindow.opener = null;

    return;
  }

  stopPolling();
  window.location.href = payUrl;

  return;
}

if (payType === 1) {
  markPaymentReturn();
  stopPolling();
  window.location.href = payUrl;

  return;
}
```

## 5. sessionStorage 保存了什么

支付前会保存一份未完成订单，方便用户从支付页面返回后恢复状态。

### 5.1 `checkout-pending-payment`

保存未完成支付订单：

```ts
type PendingPayment = {
  amount: number | null;
  orderId: number;
  packageName: string;
  payType: 1 | 3;
  payUrl: string;
  points: number | null;
};
```

用途：

- 回到 `/checkout` 后继续查订单状态。
- 移动端支付跳转回来后可以继续轮询原订单。

### 5.2 `checkout-payment-return`

值为 `"1"` 时表示用户刚从支付流程跳出去过，页面需要给订单状态恢复一点时间。

用途：

- `/checkout` 用它判断是否是支付回跳，然后恢复轮询。
- `/my-orders` 用它在登录态恢复前显示“正在恢复订单状态”，避免立刻跳登录页。

## 6. 回跳恢复逻辑

当用户回到 `/checkout`，页面会读取 `checkout-pending-payment`：

```text
页面加载
  ↓
等待用户状态 hydrated，并且 token 存在
  ↓
读取 checkout-pending-payment
  ↓
GET /app/recharge/orders/{orderId}
  ↓
如果 status = paid：
  - 刷新用户积分
  - 清理支付状态
  - 提示支付成功
如果 status = failed：
  - 清理支付状态
  - 提示支付失败
如果 status = pending：
  - 移动端 payType=1/3：只有检测到 checkout-payment-return 时才启动轮询
```

这段逻辑的核心目的是：移动端跳出当前站点去支付后，回来仍然能知道之前是哪一笔订单。

## 7. 订单轮询规则

轮询函数是 `pollOrderStatus(orderId)`。

当前规则：

| 配置 | 值 |
|---|---:|
| 轮询间隔 | 3000 ms |
| 最大轮询次数 | 100 次 |
| 最长等待时间 | 约 5 分钟 |

轮询结果处理：

| 订单状态 | 前端处理 |
|---|---|
| `pending` | 继续轮询 |
| `paid` | 停止轮询，刷新用户积分，清理本地支付状态，提示成功 |
| `failed` | 停止轮询，清理本地支付状态，提示失败 |

离开页面、路由切换、页面隐藏时会停止轮询，避免无意义请求和内存泄漏。

## 8. 后续常见修改点

### 8.1 要调整移动端支付类型

改这里：

- `pages/checkout/index.tsx` 的 `PayType`
- `resolvePayType()`
- `handlePurchase()` 里不同 `payType` 的跳转分支
- `api/recharge.ts` 一般不用改，因为 `payType?: number` 已经能传数字

比如要接支付宝 H5，可以先把类型改成：

```ts
type MobilePayType = 1 | 3 | 11;
```

然后在 `resolvePayType()` 或新的支付方式选择控件里返回 `11`，最后在 `handlePurchase()` 中明确处理 `payType === 11` 的跳转。

### 8.2 要改移动端从新窗口打开为当前页跳转

目前普通移动端 `payType = 3` 优先使用：

```ts
window.open(payUrl, "_blank", "noopener,noreferrer");
```

如果产品希望移动端行为更稳定，可以改成直接：

```ts
window.location.href = payUrl;
```

这样用户不会被新标签页分流，但返回当前页面的体验要结合支付渠道实际回跳地址一起测试。

### 8.3 要加“继续支付”按钮

可以复用 `checkout-pending-payment` 中保存的 `payUrl`。

建议位置：

- `/checkout` 恢复到 `pending` 状态时展示按钮。
- `/my-orders` 的待支付订单卡片上展示按钮。

注意：继续支付前要确认订单没有过期，并且后端是否允许复用旧的 `payUrl`。

### 8.4 要调整轮询时间

改这两个常量：

```ts
const MAX_POLL_TIMES = 100;
const POLL_INTERVAL_MS = 3000;
```

当前提示文案里写了“请在 5 分钟内完成支付”，如果轮询时间改了，记得同步改文案。

## 9. 接手时优先检查的风险点

1. `payType = 11` 文档有写，但代码没实现。
2. 普通移动端用 `window.open` 打开支付链接，部分浏览器可能拦截或让用户停留在新标签页。
3. 移动端支付完成后是否能稳定回到本站，取决于后端或支付渠道配置的回跳地址。
4. 如果用户支付后没有回到 `/checkout`，前端不会主动知道支付成功，只能在订单页或刷新用户信息时体现。
5. `sessionStorage` 只在当前浏览器标签/会话有效，换浏览器或清理会话后无法恢复本地 pending 状态。

## 10. 修改后自测清单

改动移动端支付逻辑后，至少测这些场景：

| 场景 | 预期 |
|---|---|
| 微信内置浏览器购买 | 创建订单时传 `payType=1`，随后跳转 `payUrl` |
| 普通手机浏览器购买 | 创建订单时传 `payType=3`，随后打开或跳转 `payUrl` |
| 支付成功后回到 `/checkout` | 能查到订单 `paid`，刷新积分，清理本地支付状态 |
| 支付失败 | 提示支付失败，停止轮询 |
| 未登录点击购买 | 提示登录，并跳转 `/login` |
| 刷新 `/checkout` | 能读取未完成订单并恢复状态 |
| 进入 `/my-orders` | 支付回跳期间不会立刻误跳登录页 |
